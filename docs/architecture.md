# Architecture

OndolSaem is a model host: it owns model files, loads models, keeps them in memory by policy and runs inference for client apps over a bound service. Clients never load models themselves. Code map (`app/src/main/java/io/github/sonanjip/ondolsaem/`): `catalog/` (categories and curated models), `download/` (resumable downloads in WorkManager), `engine/` (LiteRT-LM embedding and chat, ML Kit OCR, sherpa-onnx speech), `runtime/` (`ModelRuntime`, `LeasedResource`, `PriorityGate`, `KeepAliveService`), `service/` (`HostService`, `CallerCheck`, `ClientRegistry`, `ModelChangeNotifier`), `settings/`, `ui/`. The contract and client live in `sdk/`.

## Service contract (`:sdk`)

One AIDL interface per model category, reached from a small entry point, so a new category adds an interface without touching existing ones. Methods are only ever appended; clients check `apiVersion()` before calling newer methods.

| Interface | Methods |
|---|---|
| `IOndolSaem` (entry) | `apiVersion()`, `categories()`, `activeModel(category)` → `ModelInfo(category, id, displayName, version, ready, audio, vision, contextTokens)`, `getCapability(category)` → `IBinder`, `hello(ClientInfo, IClientCallback)` → `HostInfo` (version exchange, see below), `unregisterClient(IClientCallback)`, `acquire(category, clientToken)` → `ILease` (keeps a model loaded, e.g. for one chat turn; dropped when the client process dies) |
| `IEmbeddingService` | `embedQuery`, `embedDocument`, `embedImage(pfd)`, `embedImages(pfd[])`, `embedAudio(pfd)`; every result carries `modelId` + `modelVersion` |
| `IChatService` | `reply(request, IChatCallback, IToolExecutor, priority)` returns at once and streams tokens; tool calls are executed in the client through `IToolExecutor.execute(name, argsJson)`; `cancel(requestId)`, `reset()`. The conversation key is prefixed with the client package. |
| `IOcrService` | `recognize(pfd)` |
| `IAsrService` | `canTranscribe()`, `speechSpans(pfd)` (VAD), `transcribe(pfd, fromMs, ICueCallback)`; API 5 adds request-scoped `transcribeWithLanguage`; input is raw 16 kHz mono 16-bit PCM; the callback returns false to stop |
| `IFaceService` (API 2) | `detectFaces(pfd)` → `FaceResult[]` (box in 0..1 image coordinates, quality 0..1, L2-normalized 128-d `vector`, `modelId`, `modelVersion`) |
| `IDecisionService` (API 3) | `entail(premise, hypotheses[], priority)` → `float[]`: per hypothesis the probability (0..1) that it follows from the premise (at most 64 hypotheses, premise cut to 8000 characters and to the model's window); API 4: `entailImage(pfd, hypotheses[], priority)` → `float[]` |
| `IImageGenService` (API 4) | `generateImage(prompt, seed)` → `byte[]` (PNG 768×768) |

- Large inputs (images, WAV, PCM) go as `ParcelFileDescriptor` because of Binder's ~1 MB transaction limit; the host then needs no storage permission.
- Every request carries a priority: `INTERACTIVE` (chat, search queries) runs before `BACKGROUND` (indexing); background requests of several apps take turns.
- Errors: `ServiceSpecificException` is not public API, so the host throws `IllegalStateException("ondolsaem:<code>:<message>")` (`HostErrors`), which the client turns into `HostCallException(code)` with the codes in `OndolSaem.Errors` (`MODEL_NOT_READY`, `MODEL_FAILED`, `BAD_INPUT`, `CANCELLED`). A refused caller gets a `SecurityException` (client: `HostUnavailableException(NOT_ALLOWED)`).
- `OndolSaemClient` in the SDK binds on first use (`BIND_AUTO_CREATE | BIND_IMPORTANT`), retries a call once when the host process died (not chat), unbinds after an idle minute, detects a missing host (`isInstalled()`, `launchIntent()`), and exposes suspend functions and a chat `Flow`.

## Faces

Category `face` (API 2, model `face-sface`): ML Kit face detection (bundled, accurate mode, all landmarks, faces at least 5 % of the image and 40 px) finds the faces; each face with all five landmarks (eyes, nose base, mouth corners) is warped with a least-squares similarity transform onto SFace's 112×112 template (the ArcFace reference points, as OpenCV's `FaceRecognizerSF.alignCrop`) and embedded by SFace (OpenCV Zoo, MobileFaceNet trained with the SFace loss, 128-d, input NCHW RGB 0..255), then L2-normalized. The quality score is `1 − (|yaw| + |pitch|) / 90°`. Clients compare vectors with the cosine similarity; OpenCV's threshold for "same person" is 0.363 (measured on the emulator with photos of five public figures: same person 0.54 to 0.90, different people at most 0.22).

SFace runs on the ONNX Runtime that sherpa-onnx already ships (`libonnxruntime.so`, 1.28.2). A second ONNX Runtime (for example `onnxruntime-android`) cannot be added: both libraries are called `libonnxruntime.so` and their symbols are versioned per release (`OrtGetApiBase@VERS_1.28.2`), so one copy cannot serve both. `engine/OrtModel` therefore reaches sherpa's copy through a small JNI bridge (`src/main/cpp/ort_bridge.cpp`: `dlopen` + `OrtGetApiBase`; one float input, or several int64 inputs of one shape, and the first float output; graph optimization level selectable), built with CMake against the ONNX Runtime C API headers in `src/main/cpp/include` (MIT). When sherpa-onnx moves to a new ONNX Runtime line, update those headers to the same line.

## Decisions

Category `decision` (API 3): yes/no answers with a probability. The model is mDeBERTa-v3-base fine-tuned for natural language inference in 27 languages including Korean (`MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7`, ONNX export of `onnx-community`). A question becomes a statement (*hypothesis*) checked against the text (*premise*); clients build statements with the SDK's `Decisions.hypothesis(topic, description)` ("이 글은 여행에 관한 내용이다." / "This text is about travel.") and read answers with `Decisions.verdict` (yes ≥ 0.70, no ≤ 0.30, unsure between; starting values). P(yes) is the entailment probability of the softmax over all three classes (entailment, neutral, contradiction). The usual zero-shot reading leaves neutral out, but then unrelated topics look likely: on 9 Korean notes against 8 topics it gave 21 false yes at 0.70, against 6 with neutral kept (16 of 17 single questions right). `engine/NliDecider` batches up to 8 hypotheses per run over a 320-token window (premise cut first); `engine/UnigramTokenizer` is a Kotlin port of the model's SentencePiece unigram tokenizer (NFKC with the exceptions of the model's table, whitespace runs folded, Metaspace, Viterbi), checked against Hugging Face `tokenizers` by `UnigramTokenizerTest`.

The published int8 builds (dynamic quantization: activations to uint8 per tensor) answer wrongly on sherpa-onnx's ONNX Runtime 1.28.2 for Android (and on desktop ONNX Runtime without graph fusions, or below 1.24: logits near zero, probabilities around 0.5). Two models therefore exist:

- `nli-mdeberta-v3-w8` (default): the fp32 original (1.1 GB) is downloaded and converted on the phone to weight-only int8 (325 MB; MatMul weights int8 per output column, the embedding table int8 per row, activations stay float). The converted graph ships in the APK (`assets/nli-w8/model.onnx`, all initializers external in `weights.bin`) with `recipe.tsv`; `engine/NliW8Converter` reads the fp32 file's initializers (a small protobuf reader, `OnnxTensors`), applies the recipe and writes `weights.bin`, then the download is deleted (`ModelSource.HuggingFace.convert`, state *Converting*). Both are made by `scripts/make-nli-w8-template.py`, whose `--check` does the same conversion in numpy; `NliW8ConverterTest` compares the two byte for byte.
- `nli-mdeberta-v3-q4`: the published 4-bit build (weights only, MatMulNBits; 845 MB because the embedding table stays fp32), no conversion.

Both give the fp32 answers within 0.01 on the test sentences. Emulator (CPU, 2 threads): about 40 ms per question, 10 questions on one note about 0.5 s.

For multimodal decisions (`d1-omni-2b`) and image generation (`iris-3b-turbo`), the upstream LiteRT distributions ship `FULLY_CONNECTED` weights as FP16 (`Const(FLOAT16) -> DEQUANTIZE -> FULLY_CONNECTED`) and host-side BF16 token embedding tables (`embed_table.npy`, `iris_embed_bf16.f32`). After verifying each downloaded file, OndolSaem converts them on the phone without extra APK assets and deletes the larger originals:

- `engine/EmbedTableQ8Converter` quantizes BF16 embedding tables row-by-row to signed int8 with one fp32 scale per row (`.q8` file, `OSQ8` v1), halving `embed_table.npy` (524 MB → 263 MB) and `iris_embed_bf16.f32` (778 MB → 390 MB). Both `LiteRtDecider` and `iris/PromptTokens` mmap `.q8` when present and fall back to BF16 if an older install kept the raw table.
- `engine/TfliteW8Converter` parses the `.tflite` FlatBuffer directly (using 64-bit external `Buffer.offset`/`Buffer.size` for >2 GiB models), quantizes every `Const(FLOAT16) -> DEQUANTIZE -> FULLY_CONNECTED` weight tensor channel-wise to int8, wires it directly into `FULLY_CONNECTED` (removing `DEQUANTIZE`, matching `ai-edge-quantizer`'s dynamic int8 format for both LiteRT GPU and XNNPACK CPU), and streams unchanged buffers in 4 MB chunks. This converts `d1-omni-2b` (`decide_L512` + `tower_G24x24`, 3.86 GB → ~1.95 GB total) and `iris-3b-turbo`'s 12 text encoder chunks and text adapter (keeping `iris_dit_pixel_f16w_dit.tflite` in fp16 to preserve final pixel quality, 11.3 GB → ~7.2 GB total).

## Chat LLM (LiteRT-LM & Gemini Nano via AICore)

The default chat models (`chat-gemma4-e2b`, `chat-gemma4-e4b`, `qwen35-2b-vl`, `lfm3-vl-2b`, `lfm3-omni-2b`) run in-process on `LiteRtChatModel`. On devices with Android AICore, `chat-gemini-nano` (`ModelSource.AiCore`) is also offered via `com.google.mlkit:genai-prompt` (`engine/GeminiNanoChatModel`, `engine/AiCoreGateway`):

- **System-managed lifecycle & memory.** AICore downloads, updates, and holds the quantized Gemini Nano weights and KV cache inside the `com.google.android.aicore` system process (~1.1–1.5 GB system RAM), so OndolSaem adds negligible app storage and host PSS overhead (~10–30 MB IPC footprint).
- **Capability & context adaptation.** `ModelRuntime.modelInfo` and `ModelRuntime.chat` cap the chat context window at 4,096 tokens when `chat-gemini-nano` is active. `GeminiNanoChatModel` queries `Feature.SYSTEM_PROMPT` and `Feature.FUNCTION_CALLING` at session start, using native `FunctionDeclaration` / `FunctionResponsePart` when supported and falling back cleanly to prompt-guided `<tool_call>` parsing (with `StreamTextBuffer` withholding raw tool tags) when an older AICore build rejects native tools.

## Versioning

Host and clients are updated independently, so every connection starts with a version exchange:

- `OndolSaem.API_VERSION` (SDK) is the contract level; named levels live in `OndolSaem.Api` (`V1` = everything in this document except the face category; `V2` adds category `face` and `IFaceService`; `V3` adds category `decision` and `IDecisionService`; `V4` adds category `image_gen`, `IImageGenService`, and `IDecisionService.entailImage`). A change to the contract (new method, new parcelable field, new category, changed meaning) bumps it, and the new method's doc names its level.
- On every (re)connection the client calls `apiVersion()` (never changes) and then `hello(ClientInfo(apiVersion, sdkVersion))`. The host answers `HostInfo(apiVersion, minClientApi, appVersion)`.
- **Host older than the client needs:** the client refuses to connect when `apiVersion()` is below its `minHostApi`, and every SDK call checks the level it needs (`call(minApi = …)`) before sending anything, so an older host never receives a transaction it does not know. Both end in `HostUnavailableException(HOST_TOO_OLD)`: the client tells the user to update OndolSaem. `supports(level)` lets a client switch features off instead.
- **Client older than the host serves:** `hello` fails with `CLIENT_TOO_OLD` when the client's level is below `HostContainer.MIN_CLIENT_API` (`HostUnavailableException(CLIENT_TOO_OLD)`): the client tells the user to update itself. Raise the minimum only when an old contract can no longer be honoured; until then a newer host serves every older level (same transaction ids, appended parcelable fields are skipped by old readers).
- The Apps tab shows each client's SDK release and level; Settings › About shows the host's level and the minimum.

## Categories

A category is a registry entry (string id, title, description, change impact, default residency), not an enum, so new ones (face recognition, fast decision models, …) are added without changing existing code.

| Category | Change impact |
|---|---|
| Embedding | `REINDEX_REQUIRED`: strong warning listing the apps that must re-embed |
| OCR, speech recognition | `DERIVED_DATA`: notice that derived text may change |
| Chat LLM, decisions, image generation | `NONE` (decisions: apps that keep answers, such as Jogakbo's tags, store the model id and ask again after the model-change broadcast) |

Each category has curated models with descriptions; one model is the category default (stored in DataStore, `HostSettings`; until the user picks one, `ModelCategory.defaultModelId` applies). The embedding default is EmbeddingGemma 2 740M (`eg2-740m`) since 0.4.0 because it also embeds audio; installs from before 0.4.0 that never picked a model keep 440M, pinned by `HostUpgrade` (otherwise every client would re-index). Clients always use the default of a category. A category whose default is not downloaded answers `MODEL_NOT_READY`; speech still offers voice activity detection (Silero VAD is bundled).

## Downloads

Downloads run in WorkManager with resume (`.part` file + HTTP Range) and a progress notification. On a metered network (mobile data or metered Wi-Fi, `ConnectivityManager.isActiveNetworkMetered`) the app warns before starting and offers "download now" or "wait for Wi-Fi" (`NetworkType.UNMETERED`, shown as "Waiting for Wi-Fi"). A model may bring extra files from the same repository (`ModelSource.HuggingFace.extras`, e.g. a tokenizer), each with its own SHA-256, and may be converted after the download (*Converting for this phone…*, see Decisions). After the download the file is checked against the SHA-256 in the catalog (the Hugging Face LFS id; for the SenseVoice archive, the hashes of the unpacked files), shown as "Checking the file…"; a mismatch deletes the file and reports it as damaged (`DownloadException.Kind.CORRUPT`), and Retry downloads it again from the start.

## NPU

LiteRT-LM models can run on the phone's NPU when an NPU build exists for its chip. NPU builds are compiled ahead of time per chip and published next to the model in its Hugging Face repository, named `<main file>_<Vendor>_<Chip>.litertlm` (e.g. `embeddinggemma-2-740m_Qualcomm_SM8750.litertlm`).

- **Chip.** `engine/Npu.kt` reads `Build.SOC_MODEL` (Android 12+): Snapdragon `SMxxxx`/`QCSxxxx`, Dimensity `MTxxxx`, Google `Tensor Gn`; other chips (Exynos, emulators) have no LiteRT NPU. A Snapdragon chip also needs its Hexagon version (`Npu.HEXAGON`, SM8450 to SM8850 and QCS8275 so far) to pick Qualcomm's libraries; an unknown one is shown as not usable.
- **Search, not a fixed list.** `catalog/NpuDiscovery` lists the repositories of the catalog's LiteRT-LM models (`/api/models/<repo>/tree/main`, the Hugging Face token if set) and takes, per model, the file whose suffix ends with this chip; its LFS id is the SHA-256 checked after the download. So builds published after this app version are found without an update. It runs when the app is opened with NPU use on (at most once a week, kept in `files/npu-builds.json`, the last result kept offline) and from Settings › NPU › "Check again". Found in November 2026: EmbeddingGemma 2 440M and 740M for Tensor G5/G6, SM8550/SM8650/SM8750/SM8850 and MT6991/MT6993; Gemma 4 E2B for Tensor G5/G6; nothing for E4B or Qwen. The decision, face and speech models run on ONNX Runtime and are not searched.
- **Download.** Under an installed model, Models shows "Download NPU build" when the search found one for this chip, or "no NPU build of this model for <chip> yet" (the model stays on the GPU); it is stored in `files/models/<id>/npu/` next to the main file, which stays as the fallback (deleting the model deletes its NPU build). Same metered-network warning and SHA-256 check as models.
- **Libraries.** The LiteRT dispatch libraries come from `litert-npu-runtime-{google-tensor,qualcomm,mediatek}` (Apache-2.0, ~0.5 MB each; the on-device compiler plugins are excluded). Their ABI must match the LiteRT inside LiteRT-LM: the 2.3.x dispatch libraries export `LiteRtDispatchGetApi`, which LiteRT-LM up to 0.18.1 looks for; 0.19.x looks for `LiteRtDispatchQueryInterface` and fails with "undefined symbol" (seen on a Galaxy Z Fold7), so LiteRT-LM stays at 0.18.1 (as AI Edge Gallery) until matching dispatch libraries are published. 0.18.1 and 0.19.0 give identical embedding vectors (cosine 1.0, `VectorDumpTest`). `Backend.NPU(nativeLibraryDir)` gets a folder holding only this vendor's dispatch library (`files/npu/<vendor>/`, copied from the APK). Tensor and MediaTek use the vendor's libraries on the phone. Qualcomm needs its QNN runtime, which apps cannot use from the system and which is not in the APK (75 MB, Qualcomm's license): with the first NPU build, `NpuRuntime` downloads `com.qualcomm.qti:qnn-runtime` (version `NpuRuntime.QNN_VERSION`) from Maven Central, checks its SHA-256, keeps only `libQnnHtp`, `libQnnSystem` and the stub and DSP skeleton of the chip's Hexagon version (about 25 MB, `files/npu/qnn-<version>-<hexagon>/`) and copies the Qualcomm dispatch library next to them (it points the DSP's `ADSP_LIBRARY_PATH` at its own folder). The runtime is deleted with the last NPU build.
- **Loading.** Settings › NPU › "Use the NPU when available" (default on). With an NPU build and its libraries present, the embedding model tries the NPU build first (vision on the NPU; on the 740M, audio on the NPU, then on the CPU), then the GPU, then the CPU, with the main file. The chat model tries the NPU build with images on the GPU (as AI Edge Gallery does); an NPU build's context length is fixed when compiled, so a larger context setting fails there and falls back to the GPU. If the NPU build refuses an input later (fixed shapes), the embedder moves to the GPU/CPU build for the rest of its life. The dashboard shows the backend in use (NPU, GPU or CPU); the lease key carries `|npu`, so turning NPU use on or off reloads the model at its next use.
- **Silent CPU fallback.** `Backend.NPU` does not fail when LiteRT cannot load its NPU accelerator: it logs "NPU accelerator could not be loaded and registered" and runs on the CPU. `NpuLog` reads the process's own log after each NPU load and treats that message as a failure, so the next backend is the GPU, not a disguised CPU. A file without NPU-compiled parts also runs on the CPU with the accelerator registered (seen on the emulator); a real NPU build cannot, its compiled parts need the NPU, so it loads on the NPU or fails.
- **Self-check.** Settings › NPU › "Check the NPU" (`runtime/NpuSelfCheck`) is for phones that cannot be connected to a computer. For each downloaded NPU build it loads the CPU, GPU and NPU builds one at a time without fallback (`OnlyBackend`), embeds the same Korean and English documents, queries, a picture and a 1,550-character document, times them, and compares each vector with the CPU's. Verdict: identical to the CPU means the NPU did not run; a worst cosine of at least 0.98, or within 0.01 of the GPU's (the GPU already differs from the CPU, 0.976 on the picture on the emulator), means clients keep their index. A chat model's NPU build is loaded and asked one short question (first token time, tokens per second). The report adds the phone, chip, search result, NPU library files and the process's LiteRT/QNN log lines, and can be copied or shared.
- **Clients.** The model id stays the same on the NPU: an NPU build is the same model with another compiler and quantization, so its vectors must stay close to the CPU build's for clients to keep their index. The self-check and `NpuParityTest` (`scripts/npu-check.sh`, over adb) check this on the phone; the emulator has no NPU.

## Residency

Per category: keep loaded, unload right after use, or unload after 1, 2, 5 or 15 minutes (default 2). A request for an unloaded model loads it again; clients do not manage this. Each category holds one model in a `LeasedResource`: every request takes a lease, and the idle timer starts when the last lease is returned. Requests of one category run one at a time through a `PriorityGate`, where waiting interactive requests go first (in arrival order) and waiting background requests are served round-robin by app: each app has its own queue, so one app indexing thousands of files delays another app's indexing by at most one request per turn. A waiter that is interrupted (a cancelled chat) leaves its queue.

While a "keep loaded" model is in memory, `KeepAliveService` (foreground service, type `specialUse`, notification "N models in memory") keeps the host process alive; otherwise the process lives as long as clients are bound. Android may refuse to start the service while the host is in the background (Android 12+). A client in the foreground lifts the host's process state through its binding, so this happens when the client is in the background too (for example Nunsori's automatic indexing). On refusal (`KeepAliveService.start` returns false, or `startForeground` throws inside the service) `HostContainer.keepAliveBlocked` turns true: a notification on the `alerts` channel says so (tap opens the app), the dashboard shows a card with *Turn off battery optimization* (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, shown only while the host is optimized) and *Try again*. The start is retried when the app's activity starts, from the card, and on client requests (at most every 30 s), which succeeds in the background once battery optimization is off (system allow-list). Until then the model stays loaded only as long as the process does. On memory pressure (`onTrimMemory` at `RUNNING_LOW` or worse) idle models that are not "keep loaded" are unloaded.

## Model-change notifications

When a category default changes (the user picks another model with a warning for `REINDEX_REQUIRED` / `DERIVED_DATA` categories that lists the apps using it), the active model finishes downloading, or the active model is deleted:
1. Connected clients get `IClientCallback.onModelChanged(category, ModelInfo)`.
2. Every known client package gets an explicit broadcast `io.github.taehunkim.ondolsaem.action.MODEL_CHANGED` (sent with `setPackage`), which reaches apps that are not running. The SDK's manifest declares `ModelChangedReceiver` for it in every client; the app sets `ModelChangedReceiver.handler` in `Application.onCreate`. Anyone could send this action, so it is only a hint to re-check the host. The host's `<queries>` entry for the action makes client apps visible to it.
3. Clients also compare `activeModel()` with their stored value on connect, and each embedding result carries the model id.

The client decides when to redo its work (right away or when idle).

## Access control

Own apps connect directly; other apps need the user's approval. The service is exported **without a permission**; `CallerCheck` verifies the caller on every call instead: a caller is allowed when one of its packages is signed with the host's own key (`checkSignatures`) or with a certificate listed in `res/values/allowed_signers.xml` (SHA-256 hex, checked with `hasSigningCertificate`). The list holds the shared release key and the maintainer's debug key, so a debug client can use a release host and the other way round.

Any other caller goes through `Approvals` (stored as JSON in `host_settings`): a decision is kept per package **and** signing-certificate digest (SHA-256 of all signers), so an app re-signed with another key asks again. `CallerCheck.decide` returns ALLOW, DENY, ASK (unknown app or new key: record a `PENDING` request and post the notification *"<app> wants to use OndolSaem"*, which opens the Apps tab) or WAIT (already pending). Refusals are thrown as `SecurityException` whose message carries `Errors.NOT_APPROVED` in the `HostErrors` format: SDK 0.2.0 turns it into `HostUnavailableException.Reason.NOT_APPROVED`, older clients still see `NOT_ALLOWED`, so no new API level was needed. The Apps tab lists these apps under *Other apps* (signing-key fingerprint, last request) with Allow / Deny / Revoke / Forget; clients can open it with `OndolSaem.approvalIntent()` (action `ACTION_APPROVE`, own task). Allowed callers are cached per uid; any decision clears the cache, so a revoke applies to the next call.

A custom `signature` permission was dropped on purpose: Android grants a permission only if its defining app is installed first, so a client installed before the host would never get it. Third-party apps therefore use the approval path above instead of a permission.

## First run and upgrades

`HostUpgrade.run` (from `OndolSaemApp.onCreate`, before anything reads the settings) compares the stored `last_version_code` with the app's versionCode. Versions before 0.4.0 stored none, so an install counts as existing when it has downloaded models, known client apps or stored choices; such an install keeps the 440M embedding default and skips the first-run screens. A fresh install shows `ui/OnboardingScreen` instead of the tabs until it is finished (`onboarding_done`): what OndolSaem is, the apps already connected and what they use, the default model of every category with size (ticked: the categories the connected apps asked for, or all but chat when none is connected; downloads go through the usual worker, with the metered-network question), and the notification permission (asked here instead of on every start).

## Dashboard

Memory first, refreshed every 2 seconds: device memory (`ActivityManager.MemoryInfo`), the host's process memory (`Debug.MemoryInfo`: total PSS, native, graphics, Java), and per category the loaded model with backend (GPU/CPU), its memory (PSS growth measured while loading), the apps holding it, the time left before it unloads, the policy, and "load now" / "unload now". The Apps tab lists the client apps (stored in DataStore) with the categories they use and per-category request counts and average latency since the host started (`ClientRegistry`).

### API V5: recognition-language hints

SDK 0.7.0 / host 0.9.0 append `IAsrService.transcribeWithLanguage` at transaction 4. It accepts `auto/ko/en/ja/zh/yue`; legacy transaction 3 delegates to auto. Caller approval, ASR priority gating, PCM descriptor transport and cancellation remain the same. Invalid raw language codes/negative offsets are BAD_INPUT. The host API floor is unchanged.

SenseVoice takes language in recognizer configuration. `SherpaSpeech` retains one recognizer and replaces it when the requested language changes, releasing the old recognizer before loading another. ASR requests are serialized by PriorityGate and direct engine recognition by a mutex. The language never becomes a host-wide preference: every legacy call explicitly restores auto. Consecutive requests for the same language reuse the resident recognizer. No model download is required.
